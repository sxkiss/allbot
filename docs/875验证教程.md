# 875 协议适配器：登录与验证详细教程

> 实测环境：2026-11-06。875 适配器已配置且在线（`connected=true` / `qr_status=confirmed`），
> 人脸桥 `running:true`（pid 34）。本教程覆盖「重新扫码 + 人脸验证」的完整闭环。

## 0. 先判断你属于哪种情况

| 现象 | 该做什么 |
|---|---|
| 后台 875 账户 `connected=true` | 已完成，无需操作（本文仅作参考） |
| `connected=false`，二维码能出但扫码后不上线 | 大概率缺**人脸验证**，走第 3 步 |
| 点登录无二维码 / 报「账号已在线」 | 见第 5 节常见问题 |
| 换了设备类型 | 必须重新拉码（875 按设备区分拉码接口） |

## 1. 前置检查（30 秒）

```bash
# 1) 协议服务可达（应返回 200）
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18062/

# 2) 人脸桥是否正常（应 running:true）
curl -s "http://127.0.0.1:18062/api/Login/PadFaceVerifierStatus?authcode=<卡密>"

# 3) 适配器配置双开关（必须都为 true）
grep -E '^enabled|^enable' adapter/wechat_875/config.toml
```

三项都正常再往下；`running:false` 说明人脸桥进程没起，先重启协议服务容器。

## 2. 扫码登录（第一段）

1. 管理后台 →「适配器」→ `wechat_875` 卡片 →「登录」。
2. **选账号**（每个账号一张独立卡密）→ **选设备**（iPad / iPadX / Mac / 安卓 Pad / Windows / 鸿蒙 / 各海外版，共 17 种）。
3. 点「开始 / 重新登录」→ 二维码出现。
   - 二维码必须是真实 `http://weixin.qq.com/x/<uuid>`，若显示 `pwmqr.com` 套壳网址属异常。
4. 微信扫码 → 状态依次：`等待扫码 → 已扫码，等待确认 → 已确认`。
   - 后台每 2 秒轮询一次，确认后自动回填 wxid、开启心跳。

> 换设备类型后必须重新点「开始登录」拉新码；875 是「接口区分设备」，不是参数区分。

## 3. 人脸验证（第二段，关键）

新设备 / 部分账号扫码后，微信会要求**人脸验证（Pad 验证）**。它**不在适配器里**，
走 875 协议服务自身的人脸桥；不做完，`connected` 会一直是 `false`。

### 操作步骤

1. 浏览器打开（把 `<卡密>` 换成该账号的卡密）：
   ```
   http://<协议服务地址>:18062/api/Login/PadFacePage?authcode=<卡密>
   ```
   - 本机：`http://127.0.0.1:18062/api/Login/PadFacePage?authcode=<卡密>`
   - 局域网/公网：把 `127.0.0.1` 换成服务器实际 IP（18062 已监听 0.0.0.0）
   - 实测该入口返回 200，页面标题为「Pad 验证」。
2. 按页面提示在手机上完成人脸/辅助验证。
3. 验证过程由协议服务的人脸桥（mitmdump 中间人桥，只代理 `weixin110.qq.com` / `security.wechat.com`）转发，**无需在本适配器做任何配置**。
4. 完成后回到后台刷新账户状态。

### 判据

```bash
# 账户已上线
curl -s http://127.0.0.1:9090/api/adapters/wechat_875/accounts
# 期望该账户 connected=true、qr_status=confirmed
```

## 4. 接口自检（脚本化验证，可复制）

```bash
KEY=<卡密>
# 能力：应含 17 个 devices、poll=true、multi_account=true
curl -s http://127.0.0.1:9090/api/adapters/wechat_875/capabilities
# 账户列表
curl -s http://127.0.0.1:9090/api/adapters/wechat_875/accounts
# 指定设备拉码
curl -X POST http://127.0.0.1:9090/api/adapters/wechat_875/login/start \
  -H 'Content-Type: application/json' -d '{"account":"wx875_slot_main","device":"mac"}'
# 轮询状态
curl -s 'http://127.0.0.1:9090/api/adapters/wechat_875/login/status?account=wx875_slot_main'
# 协议侧登录态
curl -s "http://127.0.0.1:18062/api/Login/GetLoginStatus?authcode=$KEY"
```

### 运行态在线轮询（重要）
登录确认后，扫码轮询（2s 一次）会停止，但适配器另有**在线轮询**（默认每 30s，
可用 `onlinePollIntervalSec` 调整）向协议侧复查 `GetLoginStatus` 并实时更新 `connected`：
- 账号真掉线 → `connected` 变为 `false` 并告警
- 恢复上线 → 自动置回 `true`、同步 wxid
- WS 断开时也会主动置离线，触发状态复查与重连

所以后台 `connected` 不是登录那一刻的快照，可放心作为判据。

## 5. 常见问题（实测结论）

| 现象 | 原因与处理 |
|---|---|
| **一直 `connected=false`** | 90% 是漏做人脸验证。先查 `PadFaceVerifierStatus` 是否 `running:true`，再走第 3 步补做。 |
| **提示「账号已在线，无需重新扫码」** | 网关 `online=true` 属正常保护。需先在协议端解绑/退出，才能重新验证扫码流程。 |
| **点登录没有「登录」按钮** | `enabled=false` 或未配置 `[[wechat875.accounts]]`，实例不注册 LoginCapable。 |
| **二维码过期** | TTL 240 秒，重新点「开始 / 重新登录」。 |
| **二维码是 `pwmqr.com` 套壳网址** | 适配器已修复（`_extract_qr_content` 还原真实 `weixin.qq.com/x/`）；若仍出现，检查适配器版本。 |
| **直访 18180 报 502 `Request destination unknown`** | **属正常**，不是故障。18180 是中间人桥端口（本机未映射），mitmproxy 不知道转发目标；**人脸验证请走 18062 的 PadFacePage 入口**，不要直接访问 18180。 |
| **扫码后状态卡在「已扫码，等待确认」** | 手机端未点确认，或该账号触发了人脸验证（去第 3 步）。 |
| **`GetLoginStatus` 返回「授权码已停用 / CREDENTIAL_DISABLED」** | 大概率是**用错了卡密**（旧卡密已停用）。必须用 `adapter/wechat_875/config.toml` 里 `[[wechat875.accounts]].authcode` 实际填的那张；实测配置卡密 `status=active`、协议侧 `online=True`。 |
| **后台适配器卡片显示「已启用」却收不到消息** | 卡片徽章只反映 `enabled`（配置开关），**不是在线状态**；在线看「登录」弹窗或 `/accounts` 的 `connected`。 |
| **换设备后一直不上线** | 必须重新拉码；旧二维码对应旧设备接口。 |

## 6. 安全提示

- 卡密等同于账号凭据，不要贴到公开群或截图外发。
- 人脸验证页 `PadFacePage` 携带卡密，勿在公共网络浏览器留历史记录。
- 18180 人脸桥无鉴权，若公网暴露建议限制来源 IP 或仅走内网。
